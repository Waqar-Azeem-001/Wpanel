# Backups and recovery

Read this when you want to know **what is backed up, where it lives, which key opens it, and what to do if the server is gone.** The one-time Backblaze B2 setup and the quarterly drill are in [offsite-b2-setup.md](offsite-b2-setup.md).

## 1. What exists, where, and for how long

| What | Where it lives | Kept for | Readable by |
|---|---|---|---|
| **Nightly full backup** (01:30): the database and every uploaded file (ticket attachments, payment proofs, media) in one file `panel-postgresql-<date>-full.bak.enc` | On the server: the Docker volume `panel_backups` (`/app/panel_backups` in the web container). Off the server (once B2 is set up): bucket folder `whpanel/daily/` | Server: newest 4. B2: 30 days (`daily/`) and the one made on the 1st of each month for 12 months (`monthly/`) | **Encrypted** with the panel's key (`CREDENTIALS_ENCRYPTION_KEY`). Only the panel (or a panel with that key) can open it |
| **Pre-deploy database dump** (taken by every deploy): `predeploy-<time>.dump` | On the server: `/srv/backups/`. Off the server (once set up): `whpanel/predeploy/predeploy-<time>.dump.gpg` | Server: newest 10. B2: 30 days | Server copy: **not encrypted** (anyone with root on the server can read it). B2 copy: **encrypted to your GPG public key**; only your GPG private key opens it |
| Old dumps from before the panel had backups: `whpanel-before-*.sql.gz` | `/srv/backups/` | Newest 4 | Not encrypted. Legacy; safe to ignore |
| **The code** | GitHub, the repository `Waqar-Azeem-001/Wpanel` | Forever | Public |
| Anything that is **not** in a backup (see section 3) | `.env` on the server, Cloudflare, DNS, registrar and WHM accounts | n/a | n/a |

What the nightly bundle contains: the database (all clients, orders, invoices, payments, tickets, domains, hosting accounts, audit log, and the **encrypted** provider credentials: registrar, WHM, email), the uploaded files, and a manifest. It does **not** contain `.env`, Redis (only cache and queues), or the website files of customers' hosting (those live on the WHM/cPanel server and have their own backups there).

## 2. Which key opens what, and who holds it

| Key | Opens | Where it is | **Who must hold a copy** |
|---|---|---|---|
| `CREDENTIALS_ENCRYPTION_KEY` | The nightly bundles **and** every stored provider credential inside the database | `/srv/whpanel/.env` on the server | **Owner: a copy outside the server (password manager, plus a printed copy in a safe place).** Without it a restored database has unreadable credentials and the bundles cannot be opened. *Status: confirm that you have this copy.* |
| `DJANGO_SECRET_KEY`, `POSTGRES_PASSWORD`, `REDIS_PASSWORD`, `DJANGO_ADMIN_URL` (the rest of `.env`) | Nothing in a backup; they run the new server | `/srv/whpanel/.env` | Owner: a copy of the **whole `.env`** outside the server. It is in no backup |
| Your **GPG private key** | The `.dump.gpg` pre-deploy dumps in B2 | Only on your own computer (and an offline backup of it). **Never on the server** | Owner only |
| B2 **write-only** key (`PANEL_BACKUP_S3_ACCESS_KEY` / `SECRET_KEY`) | Nothing: it can only add files | `.env` on the server | Owner can re-create it any time in B2 |
| B2 **read** key | Lists and downloads from the bucket | Not on the server. Only used on the command line when you restore or run a drill | Owner (password manager) |
| B2 account login / master key | Everything in B2, including changing the bucket's rules | Owner's password manager (with two-factor) | Owner only |

Rule of thumb: **if the server is lost you need three things from outside it: the whole `.env`, the B2 read key, and (for pre-deploy dumps) your GPG private key.**

## 3. What is NOT backed up (and what to do about it)

- `/srv/whpanel/.env`: keep your own copy (section 2).
- Cloudflare settings (DNS records, the origin certificate rules, the firewall rules), your email DNS records (SPF, DKIM, DMARC): write them down once; they are listed in your Cloudflare account.
- The OnlineNIC allow-list of server IP addresses, the WHM server's API token and its list of allowed IP addresses: after a move to a new server the new IP address must be added at OnlineNIC and in WHM.
- Host files: `/etc/nginx/` (the site file, the Cloudflare IP list and the limits are generated by `deploy/host-nginx/harden-host-nginx.sh`), `/etc/whpanel/deploy.env`, `/usr/local/sbin/whpanel-*`, the users `deploy` and `notify` and their `authorized_keys`: recreated from `docs/deploy-setup.md`.

## 4. If this server is lost: exact steps

Time to plan for: 1 to 2 hours once you have the three things above. Do it on a **new** Ubuntu server with the same size or more.

1. **New server.** Install Docker (with the Compose plugin), nginx, certbot, git, rsync, gpg. Open only SSH (key login only), 80 and 443 in the firewall.
2. **Code.** `git clone https://github.com/Waqar-Azeem-001/Wpanel /srv/whpanel` (then `cd /srv/whpanel`).
3. **Secrets.** Put your saved `.env` at `/srv/whpanel/.env` (mode 600). It must contain the **same** `CREDENTIALS_ENCRYPTION_KEY`. Add the B2 settings if they are not in it (see offsite-b2-setup.md, section 3). If you have lost the old `DJANGO_SECRET_KEY` make a new one: everyone is signed out, nothing else is lost. Make new `POSTGRES_PASSWORD` and `REDIS_PASSWORD` values and use them in `DATABASE_URL` / `REDIS_URL` too if the old ones are gone.
4. **Start only the data services:** `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d db redis`. Wait until `db` is healthy.
5. **Get the newest backup.** The easy way, with the panel image built (`docker compose ... build web`) and your **read** key (typed here, never saved):
   ```
   docker compose -f docker-compose.yml -f docker-compose.prod.yml run --rm --no-deps \
     -e PANEL_BACKUP_S3_ACCESS_KEY=<read key id> -e PANEL_BACKUP_S3_SECRET_KEY=<read key> \
     web python manage.py offsite_fetch --folder daily --latest --to /app/panel_backups
   ```
   (Use `--folder monthly --latest` for the last monthly one, or `--name <file>` for a particular day.) The file appears in the `panel_backups` volume.
6. **Create the empty schema and restore.** Still with only `db` and `redis` running:
   ```
   docker compose -f docker-compose.yml -f docker-compose.prod.yml run --rm --no-deps web \
     python manage.py backup_panel --restore /app/panel_backups/<the file>
   ```
   This restores the database in one transaction (it either completes or changes nothing), puts the uploaded files back, runs the migrations to bring an older backup up to the current code, and clears the cache. (It first makes a safety copy of the current, empty state; that is normal.)
7. **Start everything:** `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build`, then `docker compose ... exec web python manage.py collectstatic --noinput` and `docker compose ... restart nginx`.
8. **nginx and certificate.** Run `deploy/host-nginx/harden-host-nginx.sh` for the site file, the Cloudflare IP list and the limits, then `certbot --nginx -d whpanel.myaiwhe.com` (or the Cloudflare origin certificate you use).
9. **DNS.** In Cloudflare, point `whpanel.myaiwhe.com` at the new server's address. Add the new address at OnlineNIC (API allow-list) and to the allowed addresses of the WHM API token.
10. **Check.** Sign in as a staff member; open Setup > Storage and backups (the restored backups are listed); `/status/` shows green after a minute; open one client, one invoice, one ticket attachment (proves the files came back); the Health panel on the dashboard shows no red. Make a manual backup from the Storage page and confirm it appears in B2.
11. **Re-create the deploy users** (`docs/deploy-setup.md`) and the GitHub environment secrets if they pointed at the old address.
12. **What the backup does not know.** Anything done between the last nightly backup (01:30) and the loss is gone: ask the people who ordered or paid after that time to repeat it, and check payments in the bank statements against invoices.

### Only a pre-deploy dump is available (no nightly bundle)
Download the newest `predeploy/…dump.gpg`, decrypt it **on your own computer** (`gpg --decrypt file.gpg > file.dump`; your private key never goes to a server), copy the `.dump` to the new server, then `docker compose ... exec -T db pg_restore -U <user> -d <db> --clean --if-exists --no-owner file.dump`. Uploaded files are not in a dump; if the volume `panel_backups` bundle exists anywhere use it for the files.

### Only part of the data is broken (not the whole server)
Use the panel: Setup > Storage and backups > Restore (or upload a downloaded file). It always saves the current state first, so a restore can be undone.

## 5. Proving it works: the quarterly drill

Every three months (calendar reminder), follow offsite-b2-setup.md section 6. It downloads the real off-site files, decrypts them, restores them into a throwaway database that cannot reach the live one, and compares row counts with the live database. Write the result below.

| Date | Who | Bundle used | Result |
|---|---|---|---|
| 2026-10-25 | Claude (tooling test, local files, no B2 yet) | `daily` 2026-10-25 01:30 bundle and a pre-deploy dump | 101 tables restored; 0 tables with fewer rows live; only rows added since the backup differ |
| 2026-10-25 | Claude ("server lost" rehearsal: steps 6 of section 4, into an **empty** database on a throwaway PostgreSQL and Redis, from the saved `.env`) | `daily` 2026-10-25 01:30 bundle (local copy) | 0 tables became 101; users 3, clients 1, invoices 1, orders 1; migrations ran; the stored registrar credentials opened with the saved key. The B2 download step is not tested yet (no bucket) |
