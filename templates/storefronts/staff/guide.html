Connecting an external storefront

Exactly what exists today, which value comes from where, and what it is for.

No WordPress plugin exists yet. Connecting a storefront here gives you a credential and a read-only API - it does not, by itself, make anything appear on a real WordPress site, because nothing is installed there yet to use it. Everything below is the side that is already built and tested; the last section explains what a plugin (or any other integration) would still need to do.

1. Connect a storefront

System → External storefronts → Connect a storefront. Before any connection exists, the list is empty:

Fill in a name (for your own reference only - it is never sent anywhere) and the site's own address, then Connect:

  • Name - whatever helps you tell storefronts apart later. Internal label only.
  • Website - the storefront's own address. Recorded for reference; nothing is fetched from it.
  • Integration type - WordPress today, the only kind this project currently models.
  • Webhook URL - optional; leave blank unless you already want catalog-change pings (see section 5).

2. Copy the credential - shown exactly once

The moment you connect, the page flashes the only time the raw secret ever exists outside this one message:

ValueWhere it comes fromWhat it is for
Public id (sf_...) Generated automatically when you connect; also shown permanently on the storefront's own detail page afterwards - not secret, safe to note down any time. Identifies which storefront is calling, the same way a username identifies an account.
Secret (the long random string) Generated automatically, shown only in this one flash message. Walking away without copying it means rotating for a new one. Proves the caller really is that storefront. Both values together go in one HTTP header - section 3.

If you lose it, there is no "show secret again" anywhere, on purpose. Use Rotate secret on the storefront's own detail page for a new one - this invalidates the old one immediately.

3. What the two values are actually used for

Whatever eventually calls the API (today: nothing; in future: a WordPress plugin, or any other script) sends both values in a single request header, on every request:

Authorization: Storefront sf_ARLezQj_-6P64Mn1:hIGfPQb6Gx_2NGMr_ASpioGlPLFjacz3X4LeZsPLpYQ

That is the entire authentication mechanism - no login form, no session, no cookie. A request with a missing, wrong or disabled storefront's credential gets 401 Unauthorized and nothing else.

4. Choose which plans this storefront may show

A storefront sees nothing until a plan is explicitly published to it - connecting one does not expose your whole catalog. Open a plan (Commerce → Products & plans → (a plan) → External storefronts), switch on Publish externally if it is not already, tick the storefront under Available on, and save:

The storefront's own detail page then lists everything published to it:

Two independent switches control visibility, and both must be on: Publish externally (on the plan - a global kill-switch) and Available on (per storefront, which specific ones show it).

5. What calling the API actually returns

EndpointReturns
GET /api/v1/storefront/products/Every plan published to this storefront.
GET /api/v1/storefront/products/<slug-or-id>/One plan, same shape.
GET /api/v1/storefront/categories/Only categories that hold a published plan.
GET /api/v1/storefront/addons/Every active add-on (global, not per-storefront).
GET /api/v1/storefront/domains/pricing/Every active TLD's register/renew/transfer price.

No pagination - a storefront fetches and caches the whole response. The full shapes and a worked example are in docs/e13-storefront-integration.md. The golden rule for anything that ever consumes this API: it only ever displays what these return and links "Order now" straight to each plan's order_url - the customer finishes the purchase on this portal's own checkout. It never calculates a price, a discount or tax itself. Optional webhook pings (a signed "please refetch" signal, no catalog data) are covered in the same doc.

If/when a WordPress plugin gets built

It would need to, at minimum:

  1. A settings screen inside WP admin where staff paste the public id and secret from section 2.
  2. Store them in WordPress options - server-side only, never in a cookie or anything a visitor's browser can read.
  3. Call the endpoints in section 5 with the Authorization header from section 3, from the server side, on a schedule.
  4. Cache the result and render it as whatever the site's own plans/pricing page looks like.
  5. Link every "Order now" button straight to that plan's own order_url - never build a cart or collect payment details inside WordPress itself.

None of this exists yet. This page is what whoever builds it would start from.
